# Can InkSend render an image in any language?

This is about the **rendered image content** — the arbitrary text a user typed into
some other app's text field, which `ImageRenderer` turns into a styled PNG. It is a
different question from the app's own UI language, which is handled separately by
`LocaleManager`/`AppCompatDelegate` per-app locale selection (see the "Languages" item
under `DONE:` in `todo.txt`).

## Short answer

Yes. Any Unicode script the device has fonts for renders as proper glyphs, is wrapped
at the right boundaries, and is auto-fit to a legible size — including scripts that
don't put spaces between words (Chinese, Japanese, Thai, Lao, Khmer).

## Glyph coverage

`ImageRenderer.renderBitmap()` builds its `TextPaint` with
`Typeface.create(config.font.typefaceName, Typeface.BOLD)`, where `typefaceName` is one
of Android's generic family names (`sans-serif`, `serif`, `monospace`, `cursive` — see
`FontChoice` in `StyleConfig.kt`). None of the four bundled fonts declare glyph
coverage of their own; Android resolves any code point a font doesn't cover through the
system-wide font fallback chain (the bundled Noto family), the same mechanism
`drawEmojiBadge()` already relies on for emoji. In practice this means Latin, Cyrillic,
Greek, Hebrew, Arabic, Devanagari, CJK, Thai and most other Unicode scripts render as
proper glyphs, not tofu boxes, on any device with the standard Android font set —
regardless of which of the four families the user picked.

Right-to-left paragraphs (Arabic, Hebrew) are handled correctly too:
`StaticLayout.Builder` defaults to the `FIRSTSTRONG_LTR` text-direction heuristic, which
picks RTL paragraph direction from the first strong-directional character, and
`Layout.Alignment.ALIGN_CENTER` centers a line regardless of its paragraph direction. So
mixed or pure-RTL input is laid out and centered correctly without any extra
configuration.

## Font-fit sizing across scripts

`findFillingFontSizePx()` binary-searches the largest font size whose `StaticLayout`
both fits the padded square's height *and* keeps `widestUnbreakableWidth(text, textPaint)`
within the content width. That safety check exists so the search never accepts a size
that only "fits" by letting Android's line breaker force-split an overlong run
mid-character (see the `longTextWrapsOnlyAtSpacesNotMidWord` test).

`widestUnbreakableWidth()` measures the spans between consecutive
`android.icu.text.BreakIterator.getLineInstance(ULocale.ROOT)` boundaries (with trailing
whitespace trimmed, since the line breaker hangs it past the edge). Those are the same
line-break opportunities `StaticLayout` uses internally, so the "widest unbreakable unit"
check matches what the real line breaker considers breakable:

- **Space-delimited scripts** (Latin, Cyrillic, Arabic, Hebrew, Devanagari, …): each
  span is a word, exactly as before.
- **Scripts without inter-word spaces** (Chinese, Japanese, Thai, Lao, Khmer): the spans
  are single characters/clusters. A whole sentence is no longer seen as one giant
  unbreakable "word", so the search doesn't shrink the font to cram the entire run onto
  one line — the text wraps normally and fills the square at the same quality a
  space-delimited language would (see the
  `spacelessScriptAutoFitsInsteadOfTreatingTheWholeSentenceAsOneWord` test).

Earlier revisions split on `\s+` here, which produced a legible but smaller-than-optimal
render for the spaceless scripts; the ICU `BreakIterator` switch fixed that.
