# Can InkSend render an image in any language?

This is about the **rendered image content** — the arbitrary text a user typed into
some other app's text field, which `ImageRenderer` turns into a styled PNG. It is a
different question from the app's own UI language, which is handled separately by
`LocaleManager`/`AppCompatDelegate` per-app locale selection (see the "Languages" item
under `DONE:` in `todo.txt`).

## Short answer

Mostly yes, with one caveat: text in scripts that don't use spaces between words
(Chinese, Japanese, Thai, Lao, Khmer, …) can end up rendered with a smaller font size
than necessary. Nothing crashes, clips, or mid-character-breaks — the auto-fit sizing
is just more conservative than it needs to be for those scripts.

## What already works

`ImageRenderer.renderBitmap()` builds its `TextPaint` with
`Typeface.create(config.font.typefaceName, Typeface.BOLD)`, where `typefaceName` is one
of Android's generic family names (`sans-serif`, `serif`, `monospace`, `cursive` — see
`FontChoice` in `TextStyleConfig.kt`). None of the four bundled fonts declare glyph
coverage of their own; Android resolves any code point a font doesn't cover through the
system-wide font fallback chain (the bundled Noto family), the same mechanism
`drawEmojiBadge()` already relies on for emoji. In practice this means Latin, Cyrillic,
Greek, Hebrew, Arabic, Devanagari, CJK, Thai and most other Unicode scripts render as
proper glyphs, not tofu boxes, on any device with the standard Android font set —
regardless of which of the four families the user picked.

Right-to-left paragraphs (Arabic, Hebrew) are handled correctly too:
`StaticLayout.Builder` defaults to the `FIRSTSTRONG_LTR` text-direction heuristic, which
picks RTL paragraph direction from the first strong-directional character, and
`Layout.Alignment.ALIGN_CENTER` centers a line regardless of its paragraph direction. So
mixed or pure-RTL input is laid out and centered correctly without any extra
configuration.

## The caveat: font-fit sizing assumes whitespace-delimited words

`findFillingFontSizePx()` binary-searches the largest font size whose `StaticLayout`
both fits the padded square's height *and* keeps `widestWordWidth(text, textPaint)`
within the content width. That safety check exists so the search never accepts a size
that only "fits" by letting Android's line breaker force-split an overlong word
mid-character (see the `longTextWrapsOnlyAtSpacesNotMidWord` test).

`widestWordWidth()` finds that widest word by splitting on `\s+`. That's the right unit
for space-delimited scripts (Latin, Cyrillic, Arabic, Hebrew, Devanagari, …), where a
"word" and a StaticLayout break opportunity are the same thing. It breaks down for
scripts that don't put spaces between words — Chinese, Japanese, Thai, Lao, Khmer — where
a whole sentence (or the whole input) can be a single whitespace-delimited "word" even
though ICU's line breaker (which `StaticLayout` uses internally) knows perfectly well how
to wrap those scripts at character/grapheme boundaries.

The effect: for such text, `widestWordWidth()` reports the width of the entire
unbroken run. If that's wider than the content area, every candidate font size the
binary search would otherwise accept looks like it "doesn't fit," even though
`StaticLayout` would happily wrap the real rendered lines within bounds. The search keeps
shrinking until the whole run's *unwrapped* width fits, which is stricter than
necessary — so the final image is legible and correctly wrapped, just smaller than the
same input would render at in a space-delimited language.

## Fixing it properly

A correct fix would replace the whitespace split in `widestWordWidth()` with Unicode
line-break analysis (e.g. `android.icu.text.BreakIterator.getLineInstance()`), so the
"widest unbreakable unit" check matches what `StaticLayout`'s own line breaker considers
breakable — including CJK/Thai/Lao/Khmer character-boundary breaks, not just whitespace.
That's a real behavior change to the sizing algorithm (and needs test coverage across
scripts), so it's left as a follow-up rather than folded into this note.
